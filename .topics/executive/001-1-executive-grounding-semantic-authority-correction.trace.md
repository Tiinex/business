# Tiinex Executive Grounding — Semantic Authority Correction

## Purpose

Provide the durable executive-level correction needed by a fresh human or LLM so Tiinex repository responsibilities and authority boundaries are not learned from obsolete Foundation-era wording.

## Current Safe Product Shape

Tiinex is an open-source project for keeping the context, provenance, authority boundaries, and continuation of work readable in artifacts you own, so a later human or tool can understand what exists, where it came from, what governs it, what remains uncertain, and how to continue without depending on one old chat, provider, application state, or hidden runtime memory.

The durable architectural ownership split is:

- **Docs** defines canonical Tiinex semantic contracts and interpretation authority.
- **Core** implements shared host-neutral mechanics against those contracts, including validation, lineage/tooling mechanics, portable authoring and transport behavior.
- **App / Viewer** provides reusable human-facing application behavior over qualified Tiinex material.
- **Site** hosts the official thin web deployment and Site-owned host/browser qualification surfaces.
- **Business** carries organizational priorities, reusable Role identity, responsibilities, financing boundaries, external obligations, process authority, human gates and manager-readable outcomes.
- **Providers / Interop / Runtime / Verses / Extensions** retain their declared repository-local responsibilities; package carriage or proximity does not move canonical authority into them.

## Authority Boundaries To Preserve

- Repository placement is an ownership/implementation signal, not automatic semantic authority.
- Core may carry exact Docs schema material for runtime qualification without becoming the canonical semantic source.
- Role identity and current session-holder binding are separate claims.
- Carrier progression, artifact filename progression and semantic Parent lineage are separate coordinates.
- A recoverable or machine-green package is not automatically accepted, release-ready, semantically canonical, or human-approved.
- Viewer and Playthings can expose product evidence and defects; presentation behavior does not become semantic truth.
- Authoring hosts should consume qualified schema creation/reference authority rather than re-declaring schema semantics independently.

## Operating Read

Current lane status, latest package hashes, open blockers, accepted-return sets and recovery carrier identity are deliberately not embedded here. Those belong in current recovery, Task, Handoff and Evidence artifacts. This artifact is stable executive grounding, not a status dashboard.

When a fresh successor needs both stable meaning and current state, compose this grounding with the current recovery carrier and the Docs-owned Anchor Successor Semantic Grounding Capsule.

## Interpretation Limits

- Does Not Mean: every repository is equally authoritative for every concern; current implementation state is encoded here; machine qualification substitutes for human acceptance; or a carried schema copy becomes canonical merely because Tooling can execute it.
- Must Not Be Used To Claim: publication/release readiness, current lane completion, current holder identity, semantic authority from repository/package placement, or permission to bypass declared Role/Process/human gates.
