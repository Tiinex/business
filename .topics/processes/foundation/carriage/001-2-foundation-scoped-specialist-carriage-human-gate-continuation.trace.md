# Foundation Scoped Specialist Carriage — Dependency And Human-Gate Continuation

## Specialist Carriage

The integration Anchor retains the recoverable full current frontier. A specialist carrier should contain the smallest set of **complete** Workspaces and exact authority/context needed to execute and verify its bounded scope. `full-source` means complete source for every Workspace the carrier claims to carry; it does not mean every repository belongs in every specialist carrier.

## Return Boundary

A specialist return is not automatically current. It remains a child candidate relative to the base it received and must be reconciled against the current accepted frontier before integration/recovery manufacture.

## Human-Test Carriage

A human-targeted dependency-sensitive carrier may deliberately carry more than a specialist implementation carrier when that is necessary to make the test self-contained and trustworthy.

For such a carrier:

- include all selected first-party source/context required by the test;
- preserve exact Role/Handoff/Task authority and current recovery context needed to interpret the result;
- give a direct front-door operator action rather than requiring dependency archaeology;
- distinguish ordinary external/public dependency acquisition from first-party Tiinex publication requirements;
- do not infer human acceptance merely because the carrier is complete or the machine gate is green.

## Interpretation Limits

Scoped carriage is transport/recovery policy. It does not redefine semantic Parent, repository ownership, schema authority, Role authority, or acceptance semantics.
