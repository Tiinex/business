## Decision

- State: accepted
- Subject: Anchor disposition of Kodax VS Code host-boundary repair and machine-acceptance return
- Decision: accept the bounded Extension VS Code host-boundary source repair for continuation, but reject promotion to a Sigma candidate because the required real Extension Host gate is both unexecuted and, as currently implemented, insufficiently broad to prove the controlling Task's operator-flow Done Criteria.

## Acceptance Basis

- The Kodax-to-Anchor carrier oriented cleanly and grounded Anchor to act through the exact selected return Handoff with no route or transport warning.
- Exact Tiinex-qualified pre-Kodax versus returned Extension VS Code source comparison shows a bounded host/test delta: five added files and ten modified files, with no deletions and no unrelated Workspace expansion. Seven changed paths are emitted `dist` artifacts; the durable implementation/test surface is limited to `package.json`, `scripts/test-extension-host.mjs`, `src/core/transportQueue.ts`, `src/operatorTrees.ts`, `src/packageBuilder.ts`, `src/vscode/outgoingParticipantController.ts`, `test/extension-host/suite.cjs`, and `test/run.mjs`.
- The returned source removes the operator command and host-array splice that could weaken an exact Core-qualified participant set after Attach.
- Public package-builder input no longer accepts participant Roles as caller-owned semantic input; routed Pack reprojects participant authority through Core immediately before manufacture.
- Persisted semantic manufacture receipts were removed from Transport restart state; restored/fresh queue items are requalified from package bytes through Core before route/transport presentation is trusted.
- The bounded participant confirmation extraction is host-owned presentation/controller work and does not introduce Role inventory, endpoint, speaker, cache, or host-local participant inference.
- Anchor direct Node execution against the returned compiled host source and exact accepted Local Core exercised the returned participant controller and a broad existing regression surface before encountering mode-specific package-binding expectations; this is supporting evidence only and not substituted for the real Extension Host gate.

## Machine-Acceptance Rejection

- Kodax correctly returned `blocked` because no VS Code CLI/Extension Host runner and no complete dependency-backed validation environment were available. That blocker remains valid and is not converted into a PASS.
- Independently, the newly added `test/extension-host/suite.cjs` does not yet exercise the complete real host/controller path required by the controlling Task. It activates the extension, checks command registration and dependency mode, and executes Discovery, Incoming, and Transport refresh commands, but it does not prove Incoming Replace, Outgoing construction, Handoff Attach, visible participant confirmation, exact participant preservation, two-Handoff Pack, produced carrier qualification, Transport routing, restart requalification of semantic state, pointerless no-routing behavior, or representative fail-fast errors.
- Therefore obtaining a VS Code executable and running the current suite successfully would still be insufficient evidence for Sigma-candidate status.
- Source-text/regex assertions, command-existence checks, direct helper tests, package integration, and partial Node regression remain useful lower-layer evidence but cannot substitute for the missing real Extension Host operator-flow acceptance.

## Accepted Technical Disposition

- Preserve the Kodax host repair as the current candidate source. Do not roll back participant immutability, Pack-time Core re-projection, or Transport requalification merely because machine acceptance remains incomplete.
- No new Core or Docs capability gap is established by this return.
- Keep `operatorTrees.ts` further refactoring out of scope unless the acceptance harness exposes an exact host-owned seam defect that cannot be tested or repaired otherwise.
- The next tranche is acceptance completion, not another open-ended implementation/refactor tranche.

## Required Next Gate

- Execute a true VS Code Extension Host acceptance under both exact Local Core and lock-qualified Published Core.
- The gate must drive the real extension controller/registered-command path far enough to prove the full controlling sequence: Incoming/Replace, Outgoing, Attach, Core-qualified participant presentation and exact-set preservation, two-Handoff Pack, qualified produced carrier/transport output, restart/reload requalification, pointerless package routing boundary, and representative fail-fast behavior.
- Test fixtures and deterministic host-interaction seams may be introduced only when they exercise the same production controller path and VS Code APIs used by normal commands; they must not bypass the host into Core helpers and then call that Extension Host acceptance.
- The runner must be reproducible from repository-owned test tooling or an explicitly qualified host capability. A global CLI may be used when qualified, but its absence must not encourage a synthetic PASS.
- Clean dependency-backed build/typecheck/package regression must also be obtained or any exact environment blocker must remain explicit.

## Authority Limits

- This Decision accepts only the bounded Kodax source repair for continued machine qualification.
- It does not accept the controlling VS Code Task as complete, authorize Sigma replay, authorize release/publication, or create remote mutation authority.
- Kodax owns only the bounded acceptance-completion implementation/test lane delegated next; Anchor retains reconciliation and Sigma-gate manufacture; Sigma remains excluded until the machine gate is actually satisfied.
