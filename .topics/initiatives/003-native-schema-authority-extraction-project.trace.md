# Native Schema Authority Extraction Project

## Project Identity

- Description: Business-level coordination boundary for extracting first-party schema authority and schema-specific companions into Native while preserving one maintained authority and avoiding a Core↔Native runtime dependency cycle.
- Boundary: Organizational why, priority, cross-Workspace outcome, and acceptance/disposition only; implementation truth remains in the owning Native/Core/Docs work artifacts.
- Related Task: [Native Schema Authority And Companion Extraction](https://github.com/Tiinex/native/blob/81475cd5509548868644d6d7e753e3a4f66cfffc/.topics/work/001-native-schema-authority-and-companion-extraction-task.trace.md)
- Evidence Basis: the pushed Native Task and its carried schema-ownership inventory Evidence.

## Project Purpose And Scope

- Description: Converge first-party schema ownership so Native owns canonical schema families and schema-specific companions, while Core owns generic schema mechanics and consumers continue through a one-way qualified composition/loading seam.
- Boundary: This Project does not redesign schema contracts merely to move ownership. Material schema-contract changes still use the Docs-local Schema Development process. Historical immutable Docs/Core references remain recovery authority when they still identify exact intended material.
- Related Task: [Native Schema Authority And Companion Extraction](https://github.com/Tiinex/native/blob/81475cd5509548868644d6d7e753e3a4f66cfffc/.topics/work/001-native-schema-authority-and-companion-extraction-task.trace.md)

## Parties And Resources

- Relevant Parties: Sigma for human intent/acceptance where reserved; Anchor for cross-Workspace integration; Native/Core/Docs authorities as defined by the bounded implementation work.
- Relevant Resources: Tiinex Work Lifecycle; Development And Acceptance; Accepted Change Landing when a distinct landing boundary exists; Docs Schema Development for any material schema-contract change; Native schema-extraction Task and its Evidence.
- Roles: existing Tiinex Role material governs responsibility boundaries; this Project does not assign Role holders by itself.

## Coordination State

- Description: Spawned implementation work already exists in Native and is classified as the technical owner. The Business Project follows outcome/disposition without copying repository implementation state. The outer applicable process is Tiinex Work Lifecycle; implementation may use Development And Acceptance, while Schema Development applies only when schema semantics materially change.
- Boundary: Process binding is an operating contract and grounding aid, not proof of execution or conformance. No schema extraction implementation is claimed complete by this Project artifact.
- Related Task: [Native Schema Authority And Companion Extraction](https://github.com/Tiinex/native/blob/81475cd5509548868644d6d7e753e3a4f66cfffc/.topics/work/001-native-schema-authority-and-companion-extraction-task.trace.md)

## Milestones And Outcomes

- Description: Establish one-way Core/Native schema composition seam; move canonical/static schema material without duplicate authority; migrate publication authority with immutable recovery; move/refactor executable schema companions safely; qualify consumers; accept/land the result; reduce terminal extraction lineage and leave only a short surviving frontier if needed.
- Boundary: Milestones describe desired coordinated outcomes rather than current completion claims. Each implementation Workspace remains authoritative for its actual qualification state.

## Interpretation Limits

- Does Not Prove: implementation completion, schema correctness, publication readiness, acceptance, landing, or release readiness by itself.
- Must Not Be Treated As: a duplicate implementation tracker, authority to create a Core↔Native package cycle, authority to mass-refresh byte-equivalent immutable references, or authority to bypass Schema Development when schema contracts materially change.
- Open Questions: exact one-way executable companion seam remains the first implementation frontier.
