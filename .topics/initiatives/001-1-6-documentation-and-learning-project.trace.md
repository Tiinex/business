# Documentation And Learning

## Project Identity

- Description: Make Tiinex approachable for a person or assistant arriving without prior Tiinex knowledge, then provide a maintainable path from a natural goal to qualified work, sensible structure, and recoverable continuation.
- Boundary: This is a durable cross-Workspace documentation and first-use outcome, not a folder taxonomy, a replacement for Tiinex schema authority, or an automatic project-scaffolding service.

## Project Purpose And Scope

- Description: Maintain one canonical, human-first Tiinex documentation lineage in Docs, beginning with a short Getting Started journey and growing into deeper guides only when a reader needs them. Make it discoverable through Native session Entries and useful to hosts including ChatGPT Web, VS Code/Copilot, and future consumers without copying its truth into host-specific instructions.
- Boundary: The purpose of guidance is to help the human or LLM identify available qualified capabilities, decide whether and when to use them, obtain schema and companion help from the actual qualified composition, and preserve working state with appropriate continuity. Guide prose must not duplicate normative schema fields, override Process applicability, grant Roles or remote permissions, or make particular artifact types mandatory merely because they are familiar.

## Parties And Resources

- Relevant Parties: Sigma retains human design and acceptance decisions; qualified Tiinex contributors can author, test, or review work within separately established authority. New human users and LLM consumers are the intended readers.
- Relevant Resources: Canonical Docs schemas and companions; Core portable schema discovery, schema-guide, authoring and carrier verification; Native Entries and Processes; Business organization and Project/Task ancestry; OpenAI and VS Code target adapters; Test 009 frozen first-use observations and associated external evidence as diagnostic input, not as embedded raw source-history.

## Coordination State

- Description: Establish the Docs Documentation Topic and separate Getting Started and Guides branches once this Project is immutable and recoverable across the Business-to-Docs Workspace boundary. Begin with one complete human-readable first-work journey and generic schema/capability discovery rather than a catalog of built-in artifact types. Leave future consumer-specific presentation and delivery to bounded host adaptations.
- Boundary: A new cross-Workspace child must not be authored until this parent exists at a qualified immutable published commit URL with verifiable exact bytes. The Project authoring checkpoint does not claim that the downstream Docs root already exists, that any host adapter has shipped, or that a first-use cold start passes.

## Milestones And Outcomes

- Description: (1) Qualify and publish this Project Parent; (2) author Documentation and two navigable Topic branches with exact cross-Workspace Parent; (3) write a small standalone Getting Started path, deepening guides only for multi-contract workflows; (4) connect reusable read-qualified Docs guidance to the correct Native Entry and discoverable schema/companion help; (5) add thin documentation links in README/VS Code surfaces; (6) test a blind first-use LLM with an unfamiliar qualified user-imported schema and independently verify full recovery.
- Boundary: Authoring success, integrity, transport qualification, a readable manual, consumer adoption, and human acceptance are distinct outcomes. No manual or helper index becomes current semantic authority simply by describing available capabilities. Avoid mandatory roles, processes, or multiple Workspaces for a simple user goal.

## Interpretation Limits

- Does Not Prove: that any new Project or Task has been selected for a novice, that a user-imported schema will be discovered, that a host extension can present the manual, or that recovery works for a fresh consumer.
- Must Not Be Treated As: a grant to auto-scaffold, auto-deploy, mutate remote GitHub repositories, claim that a schema exists from a static guide, or substitute explanatory prose for qualified schema, companion, or Process contracts.
