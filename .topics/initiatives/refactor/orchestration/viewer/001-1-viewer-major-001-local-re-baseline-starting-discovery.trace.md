# Viewer Major 001 Local Re-Baseline — Starting Discovery

## Discovery Intent

- Intent: establish the first current delta for Viewer carrier Major 001 using only the audited carried local recovery before any targeted historical remote read.
- Starting Question: what does the local recovery already prove about PoC product value, current refactor coverage, and the remaining replacement gap?

## Discovery Field

- Field: carried local `site`, `app`, `verse-native`, `core`, `docs` and `business` Workspaces materialized from the latest qualified Anchor recovery.
- In Scope: PoC product-contract inventory, current parity ledger state, existing Viewer parity lineage/acceptance, current App implementation surfaces, and Native Verse extraction readiness.
- Out Of Scope: remote PoC branch fetch, feature implementation, PoC retirement, release/deploy, and Sigma browser acceptance.
- Source Rule: local-first. Remote historical reads are deferred until one specific product-contract unknown cannot be resolved from carried evidence.


## Discovery Method

- Read the carried local Site product-contract inventory and Viewer parity lineage.
- Inspect the current local App parity ledger and relevant product surfaces without treating module presence as acceptance.
- Inspect the current local Native Verse package boundary and extraction frontier.
- Record only source-supported deltas; defer remote historical branch reads until a concrete unresolved product-contract question remains.

## Discovery Boundaries

- Local carried recovery is the default evidence source.
- Historical PoC implementation details are evidence, not authority or automatic requirements.
- No source mutation, remote mutation, release/deploy, browser acceptance, or PoC retirement is performed by this discovery.
- Current App/Site/Verse placement does not itself decide semantic ownership.

## Discovery Outcome

- Local Site already preserves an explicit PoC product-contract inventory with seven groups: Ingress/Workspace; Read/Navigate; Act/Author; Persist/Recover; History/Source; Export/Publish; Truthful Presentation.
- Viewer navigation has durable local lineage showing a prior technical qualification and Sigma human acceptance checkpoint before the later refactor decomposition. That acceptance is historical evidence, not automatic proof of the current refactored path.
- Current App parity code exposes 25 named PoC scenarios and every scenario is presently `partial`. This is an evidence posture: it means no scenario is currently declared fully proven in the assembled refactored product path, not that 25 features are necessarily broken or missing.
- Current App source visibly contains implementation surfaces for Workspace lifecycle/open/import/persistence, Feed/Tree/Lineage, artifact actions/authoring, Time Portal, GitHub publication, ordinary export and Handoff export/import. Presence of code/tests is implementation evidence but still needs product-path reconciliation.
- Current `verse-native` package is published-shaped but its `src/index.js` intentionally exports nothing until the owning extraction task qualifies runtime exports. Therefore the decomposed architecture is not yet a truthful complete Native Verse replacement even if App already contains many Viewer capabilities.
- Site is already thin enough that PoC replacement should be judged at the composed App + Verse + Provider/host path rather than by counting old Site modules.
- The current local recovery does not carry the historical `poc-monolith` branch bytes themselves. Existing Site discovery preserves a product-contract inventory from that branch, so a historical remote read is not yet justified until a concrete unknown survives local reconciliation.

## Initial Delta Classification

- KEEP candidate: distinct Feed / Tree / Lineage projections and readable Parent/Trace/Origin context.
- KEEP candidate: canonical human artifact actions including Create/Continue/Reference/Use-as, with validation and review rather than direct opaque mutation.
- KEEP candidate: durable local recovery, source-vs-local boundaries, Time Portal historical review, export/package and publication/re-ingest affordances.
- CHANGED INTENTIONALLY candidate: old monolith module boundaries and exact visual styling; these are evidence only unless a user-visible product value depends on them.
- UNKNOWN: exact remaining PoC-only interaction affordances not represented by the existing product-contract inventory or current parity tasks.
- UNKNOWN: which of the 25 `partial` App scenarios can already be upgraded to current parity after assembled browser-path evidence versus which still require implementation.
- UNKNOWN: final Native Verse extraction boundary and whether current App-owned Viewer code should move, wrap or remain shared application infrastructure.

## Next Discovery Actions

- Reconcile the seven product-contract groups against current App/Site/Verse source and existing local Viewer Tasks/Decisions/Reductions.
- For each of the 25 App scenarios, record whether the gap is implementation, composition, manual/browser evidence, intentionally changed behavior, or stale ledger status.
- Isolate any true `UNKNOWN` that requires historical PoC source bytes; only then perform the smallest targeted remote historical read.
- Produce the next Viewer carrier Major sequence without silently expanding this discovery Major into implementation.

## Interpretation Limits

- This discovery does not prove PoC parity, PoC retirement readiness, Native Verse completeness, current browser acceptance, or that all 25 scenarios need code changes.
- Local code presence is not equivalent to product-path acceptance.
- Historical Sigma acceptance remains valid evidence of what was once accepted, but current decomposed composition must be requalified where the path materially changed.
