# Tiinex Core

## Project Identity

- Description: Project for the coherent semantic model behind Tiinex artifacts, provenance, continuity, lineage, schemas, relations, coordination contracts, authority boundaries, and interpretation rules.
- Boundary: Core owns semantic coherence and canonical meaning boundaries, not host-specific UX, generic Business administration, or implementation grouping by repository.
- Related Project: [Native Schema Authority Extraction](../initiatives/003-native-schema-authority-extraction-project.trace.md)

## Project Purpose And Scope

- Description: Keep Tiinex semantics stable and explicit enough that humans, LLMs, Tooling, Viewer, and future integrations interpret the same durable artifacts without hidden provider- or host-specific meaning.
- Boundary: One Project may span Docs, Core, Native, Business, or other Workspaces when semantic outcomes require it. Repository placement does not define project identity.

## Parties And Resources

- Relevant Parties: Sigma for human intent/acceptance and qualified semantic, architecture, implementation, and review Roles as current work requires.
- Relevant Resources: canonical schema and semantic material, Core generic mechanics, Native first-party authority, Business Decisions/Processes, and qualified consumer evidence.

## Coordination State

- Description: Core is re-established as a current direction Project without reviving pre-reduction execution lineage. Existing `003 Native Schema Authority Extraction` is a current pre-portfolio transition Project related to this direction and remains on its already-published ancestry until completed or explicitly migrated through a qualified publication boundary.
- Boundary: New Core Projects/Tasks should descend from this Project after this structure is published when direct Project continuity is truthful; no new work is created merely for symmetry.

## Milestones And Outcomes

- Description: Coherent schema/authority ownership, trustworthy lineage/provenance semantics, durable Project/Task/Process boundaries, and reusable semantic contracts consumable by Tooling and Viewer.
- Boundary: Passing implementation tests does not by itself establish semantic closure; material contract changes remain subject to their specialized authority/process.

## Interpretation Limits

- Does Not Prove: that every schema is final, every semantic ambiguity is resolved, or the current schema-authority extraction is complete.
- Must Not Be Treated As: the Core repository, the Tooling project, a schema dump, or justification to move work solely to match repository names.
