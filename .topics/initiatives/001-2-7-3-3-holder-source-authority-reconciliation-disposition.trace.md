# Holder And Implementation-Source Authority Reconciliation

## Decision

- State: accepted.
- Subject: post-Test-2 reconciliation of Axiom semantic authority and Loom Core grounding/introspection mechanics.
- Decision: adopt Axiom's separation of recipient Role compatibility, current-session binding assertion, binding authorization, durable holder identity, existing-source authority, and new-source creation authority; accept Loom's semantics-neutral projection/provenance mechanics because they preserve those distinctions without inventing authority.

## Holder Binding

- A selected Handoff recipient Role establishes compatibility only; it does not bind the consuming session.
- A current session must supply an explicit matching Role-capacity assertion.
- That assertion is act-authorizing only when qualified semantic authority permits that assignment mode for the bounded work.
- For the current Anchor Role, `Holder State: assignable per explicit session or Handoff; no permanent holder asserted` is accepted as the semantic authorization mode for an explicit bounded current-session `Anchor` binding.
- This does not establish a durable Party/person/model identity and must not be represented as one.
- If the recipient Role's holder semantics are silent, conflicting, or require another assignment instrument, a matching CLI/session assertion remains insufficient and grounding must stay fail-visible.

## Implementation-Source Authority

Keep these dimensions independent:

1. exact source identity/material;
2. existing-source use/mutation authority;
3. new-source creation authority.

Workspace carriage, completeness/boundedness, host writability, repository identity, directory adjacency, Task executability, or generic `implement` wording are mechanical/context facts only and do not grant either mutation or creation authority.

Existing-source mutation requires exact current-work authority that both resolves the implementation source and authorizes the bounded mutation/use.

New-source creation requires explicit current-work authority permitting creation and bounding the owning Workspace/repository/root and any delegated placement constraints. A recipient may choose the exact new path/name only when that bounded choice is explicitly delegated.

Explicit read-only/no-mutation authority remains a prohibition; absence of positive authority remains unresolved rather than automatically prohibited.

## Test 2 Reclassification

- Recipient Anchor Role compatibility: qualified.
- Fresh session's explicit `Anchor` binding: the assertion was validly authorizable by the qualified Anchor Role Holder Relationship once that Role material was recovered; the Anchor-to-Anchor route alone was not the authorization.
- Bounded writable Business Workspace: qualified source/material and mechanical capability only.
- Neutral executable bookkeeping Task + Business writability: did not authorize existing-source mutation or new-source creation.
- Test 2 bookkeeping implementation therefore remains diagnostic evidence and is not adopted as Business product source.

## Core Reconciliation

Accept Loom's returned Core delta:

- explicit session holder input is projected separately from semantic holder-assignment authority;
- recipient compatibility and exact assertion provenance remain visible;
- implementation-source authority remains `unresolved` absent exact upstream-qualified authority;
- Workspace Boundary and Required Context purpose remain provenance-bearing descriptive facts only;
- positive/negative upstream authority may pass through with exact provenance without Core redefining semantics;
- participant/process non-inference, bounded Workspace readiness, exact-source blockers, and Recovery behavior remain preserved.

Independent Anchor verification of the returned Core Workspace: `npm test -- --runInBand` passed 125/125 tests.

## Anchor Operating Delta

- Session-holder discipline: never self-assign from Handoff recipient, transport, provider, or chat position. Treat session assertion and assignment authorization as separate claims, and require exact Role/Relation/Decision authority for the assignment mode.
- Source-authority discipline: before source mutation or creation, recover exact current-work authority for the specific existing source and/or explicit bounded permission to create new source. If unresolved, issue the exact authority request instead of choosing a convenient repository/path.
- Preserve `grounded-to-act` as bounded route action readiness; it is not durable holder identity or whole-program orchestration readiness.

## Next Validation

Run one focused fresh-Anchor post-remediation validation that checks the holder/source distinction without embedding product-solution guidance. The validation must preserve evaluator criteria outside recipient context and distinguish at least:

- a negative source-authority case where implementation must remain unresolved;
- a positively authorized bounded session binding under the Anchor Role Holder Relationship;
- if practical in one bounded test, an explicitly authorized source case whose authority is carried by controlling current-work material rather than inferred from Workspace facts.

Production Site/Playthings sub-Anchor orchestration remains gated until that validation is dispositioned and a new Full Recovery is verified.
