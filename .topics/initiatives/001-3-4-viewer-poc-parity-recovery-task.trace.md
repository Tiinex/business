# Viewer PoC Parity Recovery

## Objective

Recover, intentionally supersede, or explicitly disposition the materially important human product behavior demonstrated by the Tiinex Site PoC before claiming the active `refactor` Viewer has PoC parity.

## Done Criteria

- PoC evidence is recovered from both `Tiinex/site` `master` and `poc-monolith`; neither branch is treated as the active implementation merely because `master` is a conventional default name.
- The active implementation target is `Tiinex/site` `refactor` until a later explicit repository decision changes that boundary.
- Human-important PoC loops are inventoried from actual PoC behavior and classified as recovered, partial, intentionally changed, rejected with reason, or still requiring evidence; absence from the current refactor parity ledger is not treated as proof that a behavior was intentionally removed.
- The current refactor parity ledger remains supporting implementation evidence rather than authority over what the PoC demonstrated.
- Technical discovery and implementation Tasks live in `Tiinex/site`, not Business. Business retains only this outcome, priority, acceptance boundary, and concise cross-repository disposition.
- Tooling prerequisites are identified before Viewer implementation. A Viewer semantic operation is not considered ready when the human UI can inspect, infer, validate, or perform something that the qualified Tooling/LLM path cannot inspect, validate, and reproduce from the same authoritative artifacts.
- Tooling-first prerequisites cover at least intake, Workspace/open-merge behavior, source boundaries, artifact/schema reading, Parent/lineage traversal, authoring actions, local-state/recovery, historical source review, export/publication, validation/findings, and truthful capability/status projection where the PoC behavior depends on them.
- Feed, Tree, and Lineage are evaluated as distinct product projections with truthful return context and declared semantic edges; presentation does not become semantic authority.
- Time Portal, Create/Continue/Reference/Use-as, source intake, persistence/recovery, and export/publication behaviors are tested against their actual PoC value where retained rather than reduced to the presence of similarly named controls.
- Machine-verifiable semantics and runtime contracts pass before Sigma is used for routine browser acceptance. Sigma's final Viewer role is comprehension, usability, actual-path fit, and other human judgments that deterministic checks cannot supply.
- Final PoC parity is not claimed from unit/integration green alone; Sigma accepts the human Viewer result after the bounded recovery work is qualified.

## Scope

- This Business Task owns the Viewer parity outcome and acceptance direction, not Site code-level decomposition.
- Preserve PoC behavior as evidence, not as immutable architecture. A behavior may be intentionally improved or rejected when the reason and replacement contract are explicit.
- Do not equate Atlas with PoC parity. Atlas remains a later spatial projection unless independent evidence establishes a specific PoC behavior it must recover.
- Do not create new canonical semantics merely to reproduce presentation. Any genuine schema-semantic gap is escalated separately to Axiom in Docs.
- Do not open broad Viewer implementation before the relevant Tooling prerequisites are practical and qualified.

## Operating Priority

Sigma set the current Foundation ordering as: **repository/branch grounding → CLI and LLM ergonomics → Viewer PoC parity recovery → public trust/projections → Foundation exit**. PoC discovery may proceed ahead of Viewer implementation so Tooling requirements can be derived from real product needs rather than discovered late inside Viewer work.
