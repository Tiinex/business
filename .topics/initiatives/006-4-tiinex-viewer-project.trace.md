# Tiinex Viewer

## Project Identity

- Description: Project for human-facing navigation, reading, inspection, comprehension, and interaction with Tiinex artifacts, lineage, Projects, Workspaces, provenance, and qualified current state.
- Boundary: Viewer owns presentation and human interaction outcomes; it does not redefine semantic truth or turn transient UI state into hidden Tiinex authority.

## Project Purpose And Scope

- Description: Make Tiinex understandable and operable to people without requiring CLI expertise while projecting the same explicit qualified semantics used by Tooling and LLM consumers.
- Boundary: Viewer work may span Site, VS Code, App, or future hosts where a shared human-facing outcome warrants it. Those Workspaces are not Projects by default.

## Parties And Resources

- Relevant Parties: Sigma for human actual-path observation/usability and qualified product, design, Tooling, architecture, and review Roles as work requires.
- Relevant Resources: Site/reference surfaces, VS Code host, App surfaces, shared Core/Tooling projections, Business Project material, and canonical semantic authority.

## Coordination State

- Description: Viewer is re-established as a durable direction Project; no historical Viewer implementation leaf is reactivated by this artifact. New work begins only from explicit current Project/Task frontiers.
- Boundary: UI feature symmetry with Tooling is not a reason to create work. Viewer Projects/Tasks should correspond to real human outcomes and shared integration needs.

## Milestones And Outcomes

- Description: Clear Project/work navigation, visible Parent ancestry, useful Workspace/artifact browsing, understandable qualification/findings, safe shared operations, and credible public/reference presentation.
- Boundary: Presentation polish does not prove underlying semantic correctness or Tooling completeness.

## Interpretation Limits

- Does Not Prove: that Viewer is the whole Tiinex product, that every Tooling capability needs a UI, or that Site/VS Code/App are one Project each.
- Must Not Be Treated As: canonical semantic authority, a repository taxonomy, or justification for duplicating shared operational logic.
