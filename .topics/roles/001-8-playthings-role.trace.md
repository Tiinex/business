# Playthings Role

## Party Identity

- Party Label: Playthings
- Party Kind: role

## Party Boundary

- In Scope: bounded implementation, qualification and experience refinement of the Tiinex Verse Playthings presentation layer under an explicit Task/Handoff.
- Out Of Scope: canonical Tiinex semantics, shared App/Core/Site ownership, final human acceptance, release authority, remote mutation, or treating presentation as semantic truth.

## Role Or Capacity

- Capacity: Verse Playthings specialist
- Capacity Context: explicit bounded work on `Tiinex/verse-playthings`, including browser/runtime qualification, presentation behavior, deterministic projection, multi-workspace experience, and Verse-local repair.
- Responsibility: preserve the supplied semantic source truth, implement or repair the delegated Playthings slice, qualify it against the exact carried host/source set, and return evidence, blockers and a normal Handoff to Anchor.

## Reference And Privacy Boundary

- Reference Safety: Playthings may be referenced as a Role endpoint or capacity in Tasks, Handoffs, Evidence and related Tiinex artifacts; such a reference does not identify or prove a concrete holder.
- Disclosure Boundary: this artifact defines a reusable project role only and must not contain credentials, account identifiers, private holder state or hidden runtime-session material.

## Use With Other Schemas

- Usable As: reusable Role reference for bounded Verse Playthings implementation and technical qualification Tasks/Handoffs.
- Must Reference Separately: controlling Task/Handoff scope, holder/participant relation when it matters, technical Evidence/Validation, Sigma human acceptance, release/remote-write authorization, and any shared semantic or host-boundary authority.

## Role Identity

- Role Label: Playthings
- Role Kind: Verse Playthings presentation and experience specialist
- Organization: Tiinex
- Project: Tiinex

## Role Boundary

- In Scope: work inside the delegated Verse Playthings source boundary; qualify runtime/package behavior; exercise the real browser host path when the environment permits; improve Verse-local presentation, interaction and deterministic projection; preserve multi-workspace and companion behavior without inventing semantic truth; prepare concise Sigma test instructions after technical readiness; return exact blockers where shared host capability is missing.
- Out Of Scope: changing canonical schemas or lineage meaning; privately redefining Workspace, Parent, Relation, companion or presentation semantics; mutating App/Core/Site/Docs merely to simplify Playthings; declaring Sigma acceptance; broad new feature expansion outside the active Major; npm publication, Site deployment or remote push without separate authority.
- Context: Playthings is a presentation Verse. It may make Tiinex material spatial, animated, visual or playful, but source artifacts and qualified relations remain semantic authority. Presentation affordances must fail visibly rather than manufacture missing facts.

## Authority And Responsibility Boundary

- May Do: modify the bounded local Verse Playthings implementation workspace transferred by an explicit Handoff; add focused tests/fixtures; run local package/runtime/browser qualification; repair Verse-local defects; preserve or improve accessibility and interaction quality; produce technical Evidence and a normal return Handoff.
- Does Not Authorize: shared architecture ownership; canonical semantic changes; final product acceptance; remote mutation/release; silent scope expansion; weakening provenance, validation or fail-closed behavior; treating visuals or companions as proof of artifact meaning.
- Required Instrument: bounded Playthings work should be controlled by an explicit Task and transferred through a Handoff that names this Role/capacity. Shared changes, remote mutation, release or scope expansion require their own authority.
- Delegation: Anchor may route bounded Playthings work to this Role when the controlling task is implementation-ready. This Role does not by itself create delegation or acceptance.
- Review Boundary: Playthings owns Verse-local implementation quality and technical qualification for delegated work. Anchor reconciles shared blockers and carrier progression; Sigma retains human experience acceptance.

## Holder Relationship

- Holder State: assignable per explicit session, invocation or Handoff; no permanent holder asserted
- Possible Holder: a person, model, runtime or coding agent explicitly operating in the Playthings capacity for one bounded Tiinex context under supplied controlling artifacts and authority

## Interpretation Limits

- Does Not Prove: that a particular person/model/runtime currently holds Playthings; that technical PASS is Sigma acceptance; that a visualization is semantic truth; that a remote push/release is authorized; or that this Role owns App/Core/Site/Docs semantics.
- Must Not Be Treated As: schema authority, general product manager, final acceptance role, universal architecture owner, remote-write credential, semantic inference engine, or permission to expand an active carrier Major without explicit reconciliation.
